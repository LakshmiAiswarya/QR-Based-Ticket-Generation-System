Stree Shakti Ticket Portal — Technical Overview

Last updated: April 25, 2026

==================================================
1. WHAT THIS REPOSITORY IS
==================================================

A full-stack APSRTC conductor terminal for issuing tickets under the
Stree Shakti welfare scheme. The app is designed for field use on mobile
devices and runs entirely offline — no external AI API is required.

Core capabilities:

- Aadhaar identity extraction via QR decode (jsQR) or OCR (Tesseract.js)
- Passenger face verification via neural face recognition (face-api.js)
- Stree Shakti eligibility check (female AP residents get free travel)
- ML trust scoring before final ticket approval
- Local SQLite storage with optional cloud sync
- Training data export for ML model retraining

The app enforces Aadhaar-only issuance. Non-Aadhaar documents, invalid
photos, and low-confidence scans are rejected before a ticket is created.

==================================================
3. SCAN PIPELINE — HOW AADHAAR DATA IS EXTRACTED
==================================================

The scan pipeline in Scanner.tsx follows this waterfall:

Step 1 — QR decode (primary path, ~5 ms)
  - Camera frame → canvas pixel buffer → jsQR library
  - jsQR is a pure JavaScript QR decoder, no internet required
  - Handles all 5 Aadhaar QR formats:
      Format 1: Standard XML attributes (name="..." gender="..." pc="...")
      Format 2: Full XML with address fields (house, street, vtc, dist, state)
      Format 3: JSON / mAadhaar app QR ({"name":"...","pinCode":"..."})
      Format 4: UIDAI Secure QR v2 (16+ digit numeric prefix, binary payload)
      Format 5: KycRes / PrintLetterBioAuth XML (DigiLocker / e-Aadhaar)
  - Covers all Aadhaar cards issued after 2015

Step 2 — Tesseract.js OCR (fallback, ~2–4 seconds)
  - Triggered when QR decode returns no result
  - Tesseract.js v5: Google's Tesseract engine compiled to WebAssembly
  - Runs entirely in the browser — no server, no API key
  - Languages: English + Telugu + Hindi (covers all Aadhaar card scripts)
  - Language data (~14 MB) fetched from CDN on first use, cached by browser
  - Parses name, gender, and pincode from raw OCR text
  - Returns partial data (name + gender only) if pincode not found,
    triggering the front/back two-step scan flow

Step 3 — Manual entry (last resort)
  - Triggered when OCR confidence < 40% or Tesseract unavailable
  - Conductor types name, gender, and pincode directly
  - Logged as MANUAL_OFFLINE with elevated risk level (eventRiskLevel: 2)

==================================================
4. BIOMETRIC PIPELINE — HOW FACE MATCHING WORKS
==================================================

The biometric pipeline uses face-api.js, a TensorFlow.js library that
runs three neural networks entirely in the browser.

Models loaded from jsDelivr CDN (~6 MB total, cached after first load):
  SsdMobilenetv1     — face detection (bounding box)
  FaceLandmark68Net  — 68 facial landmark points
  FaceRecognitionNet — 128-dimension face descriptor vector

Matching algorithm:
  1. Detect face in ID card image → compute 128-dim descriptor A
  2. Detect face in live selfie   → compute 128-dim descriptor B
  3. Euclidean distance(A, B) < threshold → MATCH

Thresholds (Euclidean distance, lower = stricter):
  ID_CARD:   0.55  (ID photo vs live selfie — most different conditions)
  HISTORY:   0.50  (two live photos of same person)
  CONDUCTOR: 0.50  (conductor re-login)

Fallback (when face-api models fail to load):
  Pixel histogram intersection similarity is used instead.
  Less accurate but never blocks the conductor.
  The conductor can use Manual Override if needed.

Biometric capture validation (validateBiometricCapture):
  Uses canvas pixel statistics — Laplacian variance (sharpness),
  luminance mean (brightness), and luminance std dev (contrast).
  Only rejects completely blank or lens-covered images.
  Deliberately lenient in offline mode.

==================================================
5. ML TRUST SCORING
==================================================

Before every ticket is issued, an ML trust score (0–1) is computed.
Tickets with score below 0.52 are denied.

Primary path (when ml_service is running):
  POST /api/ml/evaluate → Python FastAPI → XGBoost or scikit-learn model

Fallback path (always available, no server needed):
  services/mlDecisionPolicy.ts — local heuristic using:
    - verification method (QR > OCR > manual)
    - biometric confidence scores
    - retry count and time between attempts
    - device fingerprint entropy
    - IP risk score
    - geo location shift flag
    - event risk level

The fallback is used automatically when the ML service is unreachable.

==================================================

7. OPERATOR FLOW
==================================================

1. Login or register a conductor account.
2. Start a shift:
   - Enter vehicle number and driver ID
   - Capture a conductor selfie
   - face-api.js verifies the selfie against the stored master photo
3. Scan Aadhaar:
   - Point camera at QR code (auto-detected at 150ms intervals)
   - Or press "Photo Scan" to capture and run OCR
   - Or upload an image/PDF
   - Or tap "Enter details manually" for damaged cards
4. If front side only (no pincode): flip card and scan back side.
5. For Stree Shakti eligible passengers (female, AP pincode):
   - Capture live passenger face
   - face-api.js compares to ID card photo (first trip) or
     previous trip photo (returning passenger)
6. ML trust score computed locally.
7. Ticket issued (SUCCESS) or denied (DENIED).
8. Record saved to localStorage + SQLite, synced to backend when online.

==================================================
8. VALIDATION POLICY
==================================================

Issuance is blocked when:
  - Uploaded file is not an image or PDF
  - Image does not contain an Aadhaar card
  - OCR confidence < 40% and no QR found
  - Back-side pincode cannot be recovered
  - Passenger photo is blank or lens-covered
  - Face match Euclidean distance > threshold
  - ML trust score < 0.52

Conductor-visible messages:
  "Invalid document uploaded. Ticket issuance terminated."
  "Invalid photo uploaded. Ticket issuance terminated."
  "Not sufficient data. Ticket issuance terminated."
  "QR code not detected. Use 'Enter details manually' below."

Denied attempts are written to audit storage.

12. TROUBLESHOOTING
==================================================

OCR slow on first scan:
  Tesseract.js downloads ~14 MB of language data on first use.
  Subsequent scans use the browser cache and are much faster.
  The worker is initialised lazily on first OCR call.

Face models not loading:
  face-api.js downloads ~6 MB of TensorFlow models on first biometric check.
  The app falls back to pixel histogram similarity until models are cached.
  Retry the biometric step after a few seconds.

Port in use:
  lsof -i :3000
  lsof -i :5001

SQLite locked:
  Ensure only one backend process writes to apsrtc_local.db at a time.

Large production bundle warning:
  TensorFlow.js increases the bundle size. The build succeeds and the app
  runs correctly. The warning is non-blocking.

No API key errors:
  The app does not require any API keys. If you see a "Missing API key"
  error, it is from an older cached version of geminiService.ts.
  Hard-refresh the browser (Ctrl+Shift+R / Cmd+Shift+R).
